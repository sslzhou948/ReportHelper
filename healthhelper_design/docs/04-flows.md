## 1. 启动 + 登录 + 档案流程

> 这是用户每次打开小程序都会经历的核心动线。**核心：每次启动都先恢复 `lastProfileId`，然后根据档案状态决定显示哪个页面。**

### 1.1 首次登录（无微信登录态，无任何档案）

```
① 首页 · A 状态（未登录）
   ↓ 点击"微信一键登录"
   wx.login() → POST /api/auth/wx-login {code}
   ↓ 拿到 token + userId，写入 localStorage
   ↓ 检查 GET /api/profiles → 返回空数组
⑤ A · 首次创建档案选择（自己 / 亲属）
   ↓ 选择类型
⑤ D · 添加新档案表单
   ↓ 填写关系、姓名、病种、确诊日期等 → POST /api/profiles
   ↓ 后端返回 profileId，写入 lastProfileId
① B · 有档案 · 空数据
   ↓ 点击"上传第一份报告"
（进入上传流程，详见第 2 节）
```

### 1.2 往次登录（已有 token + 至少 1 个档案）

```
启动小程序
   ↓ 读 localStorage 中的 token
   ↓ GET /api/user/profile 验证 token
   ↓ 读 lastProfileId
   ↓ GET /api/profiles/{lastProfileId} 加载档案
   ↓ GET /api/profiles/{lastProfileId}/reports?limit=1
   ├─ 无报告 → ① B（有档案 · 空数据）
   └─ 有报告 → ① C（默认）
              如果有正在进行的后台识别任务 → ① D（带悬浮条）
```

### 1.3 切换档案

```
① C / D 顶部档案 chip
   ↓ 点击
⑤ B · 切换档案弹层
   ├─ 点其他档案 → 回 ① C/D（数据刷新为新档案）
   ├─ 点"管理 ›" → ⑤ C · 管理档案弹层
   │      ├─ 点档案的"编辑" → ④ B · 档案资料编辑页
   │      └─ 点档案的"删除" → 弹确认 → 删除
   └─ 点"+ 添加新档案" → ⑤ D · 添加新档案表单
```

### 1.4 Edge cases

| 场景 | 处理 |
|------|------|
| 登录失败 / 网络断开 | 保留 ① A，按钮转 loading 态，5s 超时显示重试 |
| Token 过期（401） | 静默尝试 refresh；失败则清 localStorage 跳 ① A |
| 当前档案被删除 | 自动选择第一个剩余档案；如果一个都没了 → ⑤ A |
| 首次登录用户拒绝微信授权 | 保留 ① A + toast"未授权将无法使用" |
| 后台识别期间切换档案 | 识别任务属于发起时的档案，不跟随切换；首页 D 悬浮条仍显示，点击进入的确认页绑定原档案 |
| 多个识别任务并发 | 首页 D 悬浮条显示"识别中（2 个任务）"，点击进入任务列表 |

### 1.5 关键 storage keys

| key | 含义 | 何时写 |
|-----|------|--------|
| `token` | 登录 token | 登录成功后 |
| `userId` | 微信账号 ID | 登录成功后 |
| `lastProfileId` | 上次使用的档案 | 切换档案 / 创建档案 |
| `pendingOcrTasks` | 后台识别任务列表 | 上传后；识别完成后清理 |
| `hint.health.metricRow` | 首次进入按指标视图的引导气泡是否已关闭 | 用户关闭后 |

## 2. 上传报告流程

> 这是产品最高频的核心流程。**v1 设计原则：每张图默认作为一份独立报告；用户主动合并多页时才合并；OCR 之后按指标科学分类自动归类。**

```
用户点击上传 CTA（首页 / 健康数据右上 / 复查完成提示）
  ↓
pages/upload/index — Step 1
  ↓
用户选图：
  ├─ 📷 拍照 → wx.chooseMedia({sourceType: ['camera'], count: 1})
  └─ 🖼 相册 → wx.chooseMedia({sourceType: ['album'], count: 9})
  ↓
已选图片以缩略图列表展示
默认：N 张图 = N 份独立报告
  ↓
（可选）用户点"合并多页 ⇆"进入多选模式
  ↓
按拍摄顺序点击属于同一份报告的图（选中顺序 = 页面顺序）
点"合并为 1 份" → 这几张图标记为同一组
（可选）点单张图放大预览
  ↓
最终图片状态：每张图属于某个组（默认是独立组）
底部按钮文案动态："开始识别（N 张 → M 份报告）"
  ↓
用户点"开始识别"
  ↓
**前端立即返回首页 ① D 状态（带悬浮条 "正在识别 N 张"），用户可继续使用其他功能**
  ↓
后端异步处理：
  Step 2（在后端进行）
  循环每份报告（每组图）：
    1. 各张图独立调 OCR
    2. 合并组内所有图的指标
    3. 按 metricKey 去重：
       - 同 key + 同值 → 静默保留一份
       - 同 key + 不同值 → 标记 conflict
    4. 返回该组的结构化结果
  ↓
**识别完成后**：
  - 后端推送微信订阅消息通知用户（"识别完成，请确认"）
  - 用户在小程序内：首页悬浮条变成"识别完成，请确认 ›"
  - 用户点通知或悬浮条 → 进入 Step 3 确认页
  ↓
Step 3：确认（multiple report cards）
  - 每份报告一张卡片
  - 卡片显示：合并的页数 / 基本信息 / 识别指标数 / 异常项 / 冲突标识
  - 卡片底部突出"查看 / 编辑详情 ›"按钮 → Step 4
  - 卡片"拆分页面"链接 → 取消该报告内的多页合并
  - 有冲突的卡片显示橙色提示条 + "处理 ›" → Step 5
  ↓
Step 4（可选）：编辑详情
  - 复用报告详情页 UI（草稿态）
  - 基本信息 / 多类别指标分组（肝功能 / 肾功能 / 血脂...）
  - OCR 不确定项黄色高亮 `!`
  - 可编辑数值、添加新指标、删除指标
  - 点"完成编辑"回到 Step 3
  ↓
Step 5（可选）：冲突处理
  - 每个冲突指标显示多个候选值
  - 单选保留哪个，或选"都不要 · 删除此项"
  - 点"应用选择"回到 Step 3
  ↓
**所有冲突处理完后，"全部保存到病例夹"按钮可点击**
（未处理冲突时按钮置灰 + 提示"请先处理 N 个冲突"）
  ↓
用户点"全部保存到病例夹"
  ↓
POST /api/reports/batch-create
  Body: [{ basicInfo, metrics, sourceImageUrls }, ...]
  ↓
后端：
  1. 校验数据
  2. 对每份 report 创建实体 + 写入 ReportMetricValue
  3. 更新 UserMetricSnapshot（最新值、趋势）
  4. 计算每份报告的 abnormalCount
  5. 返回 [{reportId}, ...]
  ↓
前端：
  - 显示 toast "已保存 X 份报告"
  - 清理 `pendingOcrTasks` 中对应的 taskId
  - 如果只有 1 份 → wx.redirectTo report-detail?id={reportId}
  - 如果多份 → wx.redirectTo health/index（按时间视图）让用户看到全部
```

### 异常分支

| 场景 | 处理 |
|------|------|
| OCR 完全失败（某张图无法识别） | 该卡片显示"未识别到内容"，可点"手动填写"补录 |
| OCR 部分成功 | 在确认卡片标记识别不确定的指标（黄色高亮 `!`） |
| 合并组识别后医院/日期/类型不一致 | 弹提示"这几张图的基本信息不同，确认合并吗？" |
| 上传中网络断开 | 保留草稿（localStorage），下次进入"上传"提示恢复 |
| 识别出非报告图片 | 该卡片显示"未识别到检查报告" |
| 用户取消保存 | 弹确认"已识别的数据将丢失" |

### 多类别报告的存储

参考 docs/05-data-model.md 第 2.5.1 节。

举例：合并了 2 页的"综合生化"报告含 18 项指标（肝功能 + 肾功能 + 血脂）：

- 存为 **1 份 Report**（type = "综合生化"）
- 18 行 ReportMetricValue 各自引用对应的 metricKey
- 在"健康数据 · 按指标"视图，这些指标会按 Metric.category 自动分配到 3 个主题下显示
- 在"健康数据 · 按时间"视图，只会看到一行"综合生化"

## 4. 新增复查计划流程

```
用户点"+ 新增"（复查 Tab 右上 / 主页下次复查右上）
  ↓
跳 pages/recheck/new
  ↓
单页表单（不用多步向导）：
  1. 选检查类型（chip 选择器）
  2. 选日期（date picker）
  3. 输入医院（input + 历史医院联想）
  4. 选择 / 编辑待办（默认 5 项已勾选）
  ↓
用户点"保存"
  ↓
校验：
  - 检查类型必填
  - 日期必填且 ≥ 今天
  - 医院必填
  ↓
POST /api/recheck-plans {type, date, hospital, todos}
  ↓
后端创建计划 → 同时注册微信订阅消息（提前 3 天 + 1 天）
  ↓
前端 wx.navigateBack 回到复查主页
  ↓
新计划出现在"之后还有"列表
  ↓
如果这是最近的一个，提升到"下次复查"卡
```

## 5. 复查完成流程（简化版）

> 上一轮我们砍掉了"完成→上传→安排下一次"的复杂闭环。简化方案：

```
方案 1：用户手动标记
  待办全部勾完 → 出现"标记为已完成"按钮
  点击 → 后端 status: done → 移到"已完成 (X)"
  
方案 2：自动迁移
  到达计划日期当天 → 主页弹"今天有复查，去医院了吗"
  用户确认 → status: done
```

**[需确认：选哪个方案，或两者结合]**

完成后：
- 不自动引导上传报告（用户随时去首页上传 CTA 即可）
- 不自动引导新增下一次（避免决策疲劳，用户自己掌握节奏）
- 已完成的计划折叠在主页底部"已完成 (12) ›"

## 7. 数据同步与一致性

**离线读**：

- 用户已加载过的数据（报告、指标、计划）写入 localStorage
- 网络不通时仍可查看
- 编辑动作（勾待办、编辑档案）先本地落地，标记 `pendingSync: true`
- 联网恢复时批量同步

**多端**（如果未来支持子女共享）：

- 通过 websocket 推送变更 / 每次进入主页 silent refresh
- 暂不做实时同步，避免并发编辑冲突

**冲突处理**：

- 服务端为准（last-write-wins）
- 用户在 A 设备编辑、B 设备也编辑时，B 的修改若与 A 冲突，提示"已有更新，是否覆盖"

## 8. 错误处理通用约定

| 错误类型 | UI 表现 |
|----------|---------|
| 网络断开 | 顶部红色横条"网络断开" + 上拉重试 |
| 后端 5xx | toast "服务暂时不可用" + 30s 后自动重试 |
| 后端 401 | 静默 refresh token，失败则跳登录页 |
| 后端 403 | toast "权限不足"，不操作 |
| 后端 404 | 列表项目消失，提示"该数据已被删除" |
| 后端 400（校验失败） | 弹错误详情 modal |
| 长时间 loading（>10s） | 显示"加载较慢，请稍候"+ 取消按钮 |
