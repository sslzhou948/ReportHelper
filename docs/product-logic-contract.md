# Product Logic Contract

本文档把设计阶段讨论过的产品逻辑固化为开发契约。进入功能开发时，前端页面、后端接口、数据模型和测试用例都应以本文为准；如需变更，先更新本文再改代码。

## 1. 开发准入结论

当前可以进入功能开发的范围：

- 微信登录、档案创建、档案切换。
- 报告上传选择、图片分组、OCR 任务发起、识别结果确认。
- 报告列表、报告详情、指标详情、趋势展示。
- 关注指标、复查计划、待办勾选、我的档案。

仍需在具体实现前确认或准备的范围：

- 小程序医疗/健康类目主体资质、隐私政策、用户协议。
- OCR 服务商和 OCR 结构化结果字段的最终映射。
- 微信订阅消息模板 ID。
- 后端部署域名、对象存储桶、HTTPS 与小程序合法域名。

## 2. 全局原则

- 产品只做健康数据管理、异常标记和复查提醒，不提供诊断、治疗、处方或医疗建议。
- 所有数据按 `profileId` 隔离。报告、指标、复查计划、OCR 任务都必须归属到发起时的档案。
- 前端展示必须忠实原始报告。异常判断以该次报告自己的参考范围为准。
- 视觉默认使用 normal 模式。适老化/大字模式进入 backlog，不在 v1 基线内拆分页面。
- 用户可以离线查看已加载数据；上传、OCR、保存、订阅消息需要联网。

## 3. 档案与登录

### 3.1 启动状态机

1. 读取本地 `token`。
2. 无 token 时展示未登录/创建档案入口。
3. 有 token 时请求用户信息和档案列表。
4. 读取 `lastProfileId`。
5. 若 `lastProfileId` 有效，加载该档案；否则选第一份档案。
6. 若没有任何档案，进入创建档案流程。

### 3.2 档案切换

- 档案切换只影响当前浏览的数据视图，不影响已经发起的 OCR 任务。
- OCR 任务完成后进入确认页时，以任务绑定的 `profileId` 为准；如果当前档案不同，前端应自动切换或在确认页顶部提示“正在确认 X 的报告”。
- 删除当前档案后，若仍有其他档案，自动切换到第一份；若没有，回到创建档案状态。

### 3.3 本地存储键

| key | 含义 | 生命周期 |
| --- | --- | --- |
| `token` | 登录 token | 登录成功写入，退出/过期清理 |
| `refreshToken` | 刷新 token | 登录成功写入，退出清理 |
| `userId` | 当前微信用户 ID | 登录成功写入 |
| `lastProfileId` | 上次使用档案 | 创建/切换档案时更新 |
| `pendingOcrTasks` | 未完成 OCR 任务摘要 | 任务发起写入，保存/取消后清理 |
| `uploadDraft` | 上传草稿 | 选图后写入，保存/取消后清理 |
| `hint.health.metricRow` | 健康数据首次引导是否关闭 | 用户关闭后写入 |
| `healthDefaultView` | 健康数据默认视图 | 上传保存后可设为 `time` |

## 4. 上传与 OCR

### 4.1 图片分组规则

- 默认规则：N 张图片等于 N 份独立报告。
- 用户主动关联多张图片时，这些图片组成一份报告。
- 选中顺序就是报告页序。
- 底部按钮必须动态显示 `N 张 -> M 份报告`。
- 同一张图片只能属于一个组。
- 取消合并后，组内图片恢复为独立报告。

### 4.2 OCR 任务状态机

| 状态 | 含义 | 前端表现 |
| --- | --- | --- |
| `draft` | 已选图，未上传 | 上传页草稿 |
| `uploading` | 图片上传中 | 进度/禁用离开风险操作 |
| `queued` | 已创建 OCR 任务 | 返回首页，显示识别中 |
| `processing` | OCR 处理中 | 首页悬浮条“正在识别” |
| `needs_confirmation` | 识别完成，待确认 | 悬浮条“识别完成，请确认” |
| `confirmed` | 已保存为报告 | 清理 pending task |
| `failed` | 整体失败 | 显示失败卡片和重试/手动填写 |
| `cancelled` | 用户取消 | 清理任务本地状态 |

### 4.3 后端 OCR 合并规则

对每个图片组：

1. 组内每张图片独立 OCR。
2. 合并基础信息、指标行、影像描述。
3. 同一 `metricKey` 且值相同：静默去重，保留置信度最高的一条。
4. 同一 `metricKey` 但值不同：生成 `conflict`，确认页必须要求用户处理。
5. OCR 置信度低于阈值的行标记 `uncertain`，编辑页用黄色高亮。
6. 如果同组图片的医院/日期/报告类型不一致，前端提示用户确认；默认以第一页基础信息为准，可在编辑页修改。

### 4.4 保存规则

- 未处理冲突时，“全部保存到病例夹”不可提交。
- 保存时前端提交用户确认后的报告草稿，而不是原始 OCR 结果。
- 后端保存成功后：
  - 创建 Report。
  - 创建 ReportMetricValue。
  - 更新 UserMetricSnapshot。
  - 计算 abnormalCount。
  - 清理对应 OCR task。
- 如果只保存 1 份报告，保存后进入报告详情。
- 如果保存多份报告，保存后进入健康数据按时间视图。

## 5. 指标与趋势

### 5.1 指标归类

- 指标分类永远来自 Metric 定义表，不继承报告类型。
- 未知指标先进入 `pending` 状态。
- 能推断类别时按报告分区建议类别；无法判断时归入 `other`。
- pending 指标可以展示和保存，但默认不参与跨报告趋势分析，直到人工/规则确认。
- 一个报告可以包含多个指标类别，例如“尿酸、电解质、血脂”套餐中同时包含肾功能、电解质、血脂、肝功能指标。报告不要求用户默认分拆；系统按指标级 `category` 归集健康数据。
- 报告类型必须保留医院原始名称，同时写入标准化类型：`originalType/type/typeKey/canonicalTypeName`。趋势、筛选、归档统计使用 `typeKey`，前端展示优先保留原始名称。
- OCR 基础信息字段必须记录来源：`ocr`、`inferred_from_batch`、`user_edited`、`unknown`。同批上传可推测医院、日期、姓名、科室等字段，但前端必须提示用户确认，不能把推测值伪装成 OCR 原文。

### 5.1.1 字段标准化分阶段策略

这些能力影响后端数据模型和接口契约，必须从当前迭代开始纳入设计：

- v1 当前迭代：数据模型、mock API、fixture、确认页展示支持 `typeKey`、指标级分类和字段来源标记。
- v1 后端联调前：后端表结构、API contract、批量保存接口落地这些字段。
- v1 管理后台前：先用静态映射表和测试 fixture 控制常见报告类型/指标。
- v1.1/运营后台：加入管理员维护同义词、未知指标审核、映射发布、系统状态监控。

### 5.1.2 自学习映射与管理员审核

系统需要支持基于真实用户报告持续完善指标和报告类型映射库，但自学习只能生成候选规则，不能直接改生产映射表。

- 用户上传报告时，如果出现未知指标、未知报告类型或低置信度归类，后端生成 `MappingReviewItem`。
- 用户报告仍可保存归档；未知/冲突指标以 `mappingStatus=pending` 或 `mappingStatus=conflicted` 保存。
- pending/conflicted 指标可以在报告详情中展示，但默认不参与跨报告趋势、首页异常汇总、关注指标推荐和健康数据聚合。
- 管理员不需要实时处理；用户侧只提示“部分指标待系统确认分类，不影响报告保存”。
- 管理员确认映射后发布到 `publishedMappingRules`，后台异步回填历史 pending/conflicted 指标。
- 回填只更新标准化字段、映射状态和派生快照，不覆盖 OCR 原文、用户编辑值、原始报告图片、原始指标名、原始单位。
- 如新映射与历史映射冲突，必须进入管理员冲突处理流程，不允许静默覆盖。

映射库分层：

- `publishedMappingRules`: 生产使用的已发布映射，前端趋势和归集只依赖它。
- `draftMappingRules`: 根据真实样本聚合出的候选映射，只供管理员审核。
- `mappingReviewItems`: 未知项、冲突项、低置信度项的审核队列。

### 5.2 异常判断

- 数值型：按该次报告的 `refRangeLow/refRangeHigh` 计算 `low/high/ok`。
- 定性型：按 `refQualitative` 计算 `positive/ok`。
- 每个历史点用该次报告自己的参考范围判断颜色。
- 趋势图参考线使用最新一次报告的参考下限；历史列表显示每次报告的具体参考范围。

### 5.3 趋势文字算法

v1 默认采用最近 3 次数据；不足 3 次时用已有数据：

- 定性型指标不显示趋势文字。
- 最近值缺失或不可解析：`无趋势`。
- 计算 `delta = latest - oldest`。
- 计算 `range = latest.refRangeHigh - latest.refRangeLow`；若 range 缺失或为 0，使用 `abs(oldest)` 的 20% 作为兜底尺度。
- `abs(delta) / range < 5%`：`平稳`。
- `5% <= abs(delta) / range < 15%`：`略上升` / `略下降`。
- `>= 15%`：`持续上升` / `持续下降`。
- 若只有 1 次记录：`首次记录`。

### 5.4 关注指标

v1 默认决策：

- “关注指标”是用户手动收藏的常看指标。
- “需要关注”是系统按异常自动判断的指标。
- 二者概念分开，但展示时异常指标可排序优先。
- 添加入口：
  - 指标详情页右上 `关注/已关注`。
  - 首页“关注指标”右上“管理”。
- 关注状态写入 UserMetricSnapshot 的 `isPinned`。

## 6. 报告管理

- 报告软删除，保留 30 天可恢复。
- 删除报告后必须重算相关指标的 UserMetricSnapshot。
- 编辑报告任一指标后必须重算该报告 abnormalCount 和相关指标趋势。
- 报告详情页指标行点击进入指标详情；趋势小图标不作为唯一入口。
- 报告原图仅保留缩略图和可过期访问 URL；生产环境不暴露永久公网 URL。
- 影像报告（如 CT、MRI、超声）v1 只做归档、查看、编辑文字所见和复查线索，不进入指标趋势分析。
- 影像报告必须保留 `modality`、`examPart`、`examMethod`。例如“胸腹盆CT平扫”可以拆成同一 `typeKey=ct_plain` 下的不同部位：胸部、腹部/盆腔。
- 如果 OCR 只能识别出“胸腹盆CT平扫”而无法区分部位，前端在确认页提示“检查部位待确认”，用户可以选择或编辑；未确认时仍可保存为影像报告，但不参与数据分析。

## 7. 复查计划

### 7.1 创建规则

必填字段：

- 检查类型。
- 日期，必须大于等于今天。
- 医院。

默认待办：

- 预约挂号。
- 准备身份证和病历本。
- 复查前一日清淡饮食。
- 复查当天空腹。
- 提前 2 小时出发。

### 7.2 完成规则

v1 默认决策：

- 用户手动勾选待办。
- 待办全部完成后出现“标记为已完成”。
- 用户点击后弹二次确认，计划状态从 `pending` 变为 `done`。
- 已完成计划进入底部折叠区。
- 不自动引导上传报告，也不自动创建下一次复查。

### 7.3 提醒规则

- 默认提醒：T-3、T-1、T-0。
- 新建计划时引导用户授权一次性订阅消息。
- 如果用户拒绝授权，计划仍可保存，仅不推送提醒。
- v1 不做提醒频次自定义；该能力进入 backlog。

## 8. 我的与档案

- 档案资料只用于健康记录展示，不参与医疗诊断。
- 数据导出 v1 作为独立页面，后端生成安全下载链接。
- 报告归档管理 v1 作为独立页面，删除/恢复/批量移动后续接入。
- 使用指南、指标说明、关于我们使用内置静态页，避免早期依赖 webview 域名。
- 退出登录必须弹确认，确认后清理 token 和本地缓存，回到未登录状态。

## 9. 隐私与合规

- 登录前必须展示用户协议和隐私政策入口。
- 报告、档案、用药、手机号等数据必须通过 HTTPS 传输。
- 手机号加密存储。
- 对象存储 URL 使用短期签名。
- 后端访问日志至少保留 6 个月。
- 应用内必须显著声明：本应用不提供诊断，仅供数据管理参考。

## 10. 未决项

进入后端联调前必须确认：

- 小程序主体资质和类目。
- OCR 服务商与费用预算。
- 微信订阅消息模板 ID。
- 用户协议与隐私政策正文。
- 后端基础设施：域名、HTTPS、对象存储、数据库。

可在功能开发中并行细化：

- 完整 Metric 预置表，建议先 100-200 个常用指标。
- 未知指标管理员审核流程。
- 数据导出文件格式。
- 家属共享和权限体系。
